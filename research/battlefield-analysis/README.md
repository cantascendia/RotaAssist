# 战况理解与独立输出优化：技术分析

2026-09-22，Astra。基于 rc.5 源码、固定版本 API 文档、上游说明和本轮真实 SimC 排除变量实验。
本文是分析和实施方案；没有将未完成的模块算作现成功能。本轮不改推荐行为、不重新安装插件。

## 结论

应当建立“可观测战况 → 各技能的有效目标与收益 → 多步比较 → 实战验证”的闭环。
暴雪建议可以保留为对照或信息不足时的候选来源，不应成为独立决策器的输入前提。
但“任意时刻完整知道战况，保证每一步都是全局最大伤害”不能由当前可用信息推出。

设两个真实战况给插件的可读信息完全一样，但最佳动作不同，则只接收这些信息的决策器
不可能在两个战况都保证选对。更多计算、预测或大模型不能消除这个信息缺口。
可以优化的是**基于可得信息的预期有效伤害**，并测量判断错误的代价和不确定性。

旧 Hekili 的公开说明是：根据角色状态和 APL 模拟后续技能，玩家改变动作后重新评估。
它也不是未来随机触发已知的全局最优证明。其 Retail 项目在 Midnight 12.0 后停止，
因此历史 Hekili 和当前版本不能直接做无条件 DPS 排名。[Hekili 上游说明](https://github.com/Hekili/hekili)

## 当前代码真正缺什么

1. `IndependentDecision.lua` 判断的是优先级条件，尚未计算候选动作的预期伤害、机会成本、
   连续动作分支或长冷却收益。能独立选出技能，不代表在比较技能价值。
2. rc.5 冻结候选没有 `active_enemies` 条件。独立观测器有数量下界输入，但选出的这份
   策略并不据此切换优先级。现有 APLEngine 的单双目标分组是另一条路径，不能混为同一能力。
3. 候选显式/隐式使用 11 类条件输入，其中 5 类在 `IndependentObserver` 没有提供：
   三个 `action.*.demonsurge_available`，`buff.initiative.up`、`buff.inertia_trigger.up`。
   这是字段映射审计，不是“实战有 45% 信息缺失”的测量。
4. 已映射的怒气、CD、充能、变身和目标 debuff，也只有公开、有效时才可用。
   当前没有真实客户端观测覆盖率，不能把完整信息模拟中的表现当作实际提示质量。
5. `TargetContext` 是近身敌人数下界和当前目标技能距离检查。它没有证明刀舞范围内目标、
   眼棱锥形内目标、以当前目标为圆心的溅射目标是同一批，也没有精确的敌人寿命模型。
6. 目前同源的是规则与条件。SimC 执行动作时的资源/伤害/移动机制尚未完整移植到 Lua；
   “同一张规则表”不意味着两个环境有同样的战斗状态和动作结果。

## 战况应该怎样表示

每项数据带 `value/interval`、来源、采样时间、目标代次、可读性和估计误差。
只在输入受影响时刷新相关缓存；切目标、换天赋、技能替换、施法失败、移动开始或光环变化
均需要使相关预测失效。任何事件参数也要先验证公开性。

| 部分 | 必要内容 | 获取和未知处理 |
|---|---|---|
| 角色构筑 | 具体天赋节点/等级、英雄树、套装、饰品、装备和属性 | 战前公开配置生成指纹；变动后模型失效，不能只认“邪痕”标签 |
| 技能状态 | 费用、生成、GCD、施法/引导、CD、充能、技能替换 | 版本和构筑对应的机制模型；即时状态逐项通过公开性检查 |
| 玩家增益 | 是否存在、剩余时间、层数、影响哪些技能 | 已验证 ID + 可读光环；无法证明不存在时保留未知 |
| 目标状态 | 有效性、自己的 debuff、可攻击性、优先级、预计剩余寿命 | 每目标独立缓存；身份不可读时使用局部 token/代次，不能假造稳定 GUID |
| 每技能覆盖 | 当前目标是否可施放、预计实际命中的敌人集合/数量区间 | 将玩家中心、目标中心、锥形、直线、链式覆盖分别建模 |
| 战斗进程 | 当前波次、预计转阶段/停手、移动、爆发窗口 | 可读事件、用户提供的路线/窗口和经过校准的估计；时间未知就保留范围 |
| 执行状态 | 已开始施法、剩余引导、输入延迟、换目标成本、失败反馈 | 支持公开读数时更新；不能把尚未执行的提示当作已施法 |

API 的 `IsSpellInRange` 说明只保证某技能对某单位的距离测试，并可能返回 nil；
它不是“这个 AoE 实际命中了几只”的接口。
[固定版本 Blizzard 生成文档镜像](https://github.com/Gethe/wow-ui-source/blob/78282522143e25c3540583734fd192c3d69be910/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellDocumentation.lua)

例如，确认三只近身敌人，并不能证明它们都在眼棱前方；确认五只在玩家周围，也不能证明
五只都在远处当前目标的溅射范围。几何不可观测时应降低命中估计的确定性，而不是编造坐标。
当前代码没有证据表明姓名板覆盖了所有敌人，因而也没有一个可信的全场数量上界。

## 如何选出更高伤害的下一步

建议实现下列过程；这不是 rc.5 已有的功能：

1. **先排除不成立的动作。** 未学会、目标无效、确定超距、无法完成引导等按证据排除。
   保留短暂等待作为候选；“永远找一个亮的技能”可能导致错失爆发衔接。
2. **比较行动组合。** 第一版以 3–6 个 GCD 的分支搜索作为待测设计，模拟资源、充能、
   伤害、dot 生效次数、增伤覆盖、溢出损失和技能重置。深度要通过收益和耗时测试决定。
3. **给更远的未来保留价值。** 搜索终点估算剩余资源和长 CD 的后续价值，避免短窗口
   把两分钟大招全部花掉、却错过即将到来的转阶段或高价值目标。
4. **对未知状态作区间或概率计算。** 可读取的本人施法和已验证机制可以更新估计；未知
   触发、费用变化和不可读事件必须扩大不确定性。不要把记账值冒充实测怒气/光环。
5. **确定性选择与预期选择分开。** 若所有合理状态都支持同一动作，给高置信建议；若
   选择依赖假设，则使用经验证的概率模型比较预期收益并标注不确定性。差异小于模型
   误差时不声称“唯一最优”，可保留稳定建议或退回参考候选。
6. **每次真实变化重算。** 显示后续技能只是条件预测；玩家打了别的技能、换目标或怪物
   离开范围后，立刻废弃旧路径。必须从实际选中的首位技能推进后续模拟。

优化目标需要固定：默认比较同一战斗窗口内的预期有效伤害，而不是不同长度窗口的
单次伤害/GCD。用户指定优先目标时，使用明确目标权重；否则不能为了刷小怪伤害而自称
优先目标最优。不可接受的生存/机制风险作为动作约束，优先级和伤害收益分别记录。

离线训练/搜索可以使用完整模拟状态作为参考，但实际策略的输入必须经过“可观测性遮罩”。
遮罩需要来自真实客户端记录的可读性，不能任意挑选一个让策略显得很强的缺失率。
完整信息策略和受限信息策略的差距应单独报告，不能靠改名掩盖。

## 四种实现途径

| 途径 | 能贡献什么 | 不能据此保证什么 |
|---|---|---|
| 游戏内公开 API | 最直接的实时观测、低延迟提示 | 并非所有战斗状态可用于逻辑判断 |
| 离线角色模拟 + 小型运行时策略 | 按具体构筑寻找策略、量化误差、降低实时计算量 | 无法把模拟器的隐藏状态变成游戏实测值 |
| 用户路线/爆发计划输入 | 提供下一波和目标优先级的先验 | 实际拉怪/战斗时长仍会偏离计划 |
| 屏幕识别研究 | 可能提取已显示的图标、读条等信息 | 遮挡、动效、识别延迟、缺失画面与未来随机性仍在；当前没有准确率或部署验证 |

屏幕识别不应直接升级为“全知”方案；它需要另行验证采集、识别、端到端延迟和适用条件。
本分析没有实现该路径，也没有给出平台规则许可结论。大型语言模型可以辅助离线研究；
实时选择应由经过预算和误差验证的数值模型或小型策略执行。

Blizzard 对 secret values 的说明区分了“能显示”与“能用于逻辑判断”。应逐接口做运行时
能力检查；也不应把政策概述误读成“所有字段永远不可读”。
[Blizzard 官方说明](https://news.blizzard.com/en-us/article/24246290/combat-philosophy-and-addon-disarmament-in-midnight)

## 实施顺序与验收

| 顺序 | 要交付的东西 | 验收证据 |
|---|---|---|
| 1 | 实战可观测性清单、候选规则依赖清单、目标代次 | 每种构筑/场景有哪些输入可读、过期或未知；不保存 secret 数值 |
| 2 | 具体构筑技能模型与每技能目标估计 | 费用、CD、重置、增伤、命中范围、目标上限分别有来源和回放用例 |
| 3 | 同一状态下候选动作收益和短期分支搜索 | 能解释 A 比 B 多多少有效伤害；含等待、移位、目标改变的成本 |
| 4 | 完整信息和受限信息的分开评测 | 同构筑/场景/动作集合对照，多种子留出验证，无信息泄漏 |
| 5 | 有门槛的独立首位推荐 | 独立首位可胜出；后续队列以该首位为起点；无效状态及时清空 |
| 6 | 实战影子评估后启用 | 判断覆盖率、非法动作率、提示延迟/抖动、帧时间及实际伤害证据 |

场景至少覆盖：1/2/3/5/8 目标、目标进出范围、单体→增援→减员、目标即将死亡、转阶段、
需要移动/中断引导、爆发前后、资源不足与溢出、施法失败、换天赋和饰品。所有结果按构筑
分别报告；静态 1/5 目标胜出也不能代表大秘境全程胜出。
SimC 的 RaidEvents 支持增援和移动等模拟场景，可作为下一轮实验工具，但它的未来事件
时间不能直接当作游戏插件实时已知信息。[SimC RaidEvents](https://github.com/simulationcraft/simc/wiki/RaidEvents)

质量门槛应同时覆盖平均收益、最差场景退化、统计误差、建议可执行性和运行耗时。
“99%”若要使用，只能注明相对于哪个参考策略、哪些场景和什么输入条件；不能叫做理论
绝对上限。当前候选尚未通过这些门槛，本分析不改变这一结论。

## 本轮诊断实验

`action-envelope.json` 保留四组参考：完整、去掉自动换目标、去掉拾取碎片、两项都去掉。
rc.5 候选保持不变。固定引擎和构筑、1/5 目标、120/300 秒、每次请求 5000 迭代、2 线程、
seed 20260925。该种子已在前轮用过，本轮是诊断而不是新的留出验收。
移除行为可能影响其他技能选择，效果不要求可加；完整参考始终保留，不能改用削弱参考
来宣布超过原参考。多线程同种子结果应按统计误差比较，不要求逐位复现相同均值。

20 次运行实际产生 99,980 个 DPS 样本，结果如下：

| 目标/时长 | 候选相对完整参考 | 候选相对移除两项后的参考 |
|---|---:|---:|
| 1 / 120 秒 | -1.416% | -0.869% |
| 1 / 300 秒 | -2.065% | -1.591% |
| 5 / 120 秒 | -1.474% | -1.276% |
| 5 / 300 秒 | -2.675% | -2.591% |

去掉自动换目标单项后的均值与完整参考非常接近，不能据此宣称换目标一般没有价值。
在这个固定构筑下，额外行为不能解释全部差距；移除两项后候选依然在四个场景落后。
本结果支持继续改进策略和机制模型，不支持宣布候选已经超过参考。
各组标准误、样本数、有效配置和原始结果哈希保留在 JSON 中。
